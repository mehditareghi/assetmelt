Everything here applies to SSG (static) and SSR (server) output modes, with mode-specific notes where the APIs differ.

## Why compress for Astro when the framework optimizes at build time

Astro's `<Image />` component is powerful — it uses Sharp to resize, convert formats, and generate responsive srcset automatically during `astro build`. That sounds like "commit anything and Astro fixes it."

Not quite. Here's what Astro **cannot** fix:

- **Oversized source dimensions** — Astro resizes at build time, but a 6000px original still wastes disk space in your repo and slows the first build before caching kicks in.
- **Already-bloated commits** — if you commit a 4 MB camera JPEG, git stores 4 MB forever. Clones are slower, LFS bills are higher.
- **Build time at scale** — every source image requires Sharp processing. Pre-compressed sources reduce CPU demand and improve CI cache hit rates.
- **Metadata exposure** — EXIF GPS and timestamps pass through unless you strip them before commit.

The winning strategy: **compress locally** → commit clean assets → let Astro handle responsive variants and format fallbacks for each visitor.

## The optimization split: you vs Astro

Think of image optimization as a two-stage pipeline:

| Stage | Your responsibility | Astro responsibility |
| --- | --- | --- |
| **Source prep** | Resize to max display width × 2, export AVIF/WebP, strip metadata, commit small files | — |
| **Build delivery** | — | Generate responsive widths, convert formats, optimize with Sharp, emit HTML |

You own the bytes before they hit the repo. Astro owns the bytes served to each visitor after `astro build`.

### What Astro Image does automatically

- Resizes images to configured widths (via `widths` prop or default densities)
- Converts to target format (WebP, AVIF, or original) based on config
- Generates responsive `srcset` and `sizes` attributes
- Applies dimension hints to prevent CLS when you provide width/height
- Optimizes with Sharp at build time and caches results

### What you must do manually

- Resize originals to reasonable max dimensions (e.g., 1920–2400px wide for heroes)
- Export to efficient formats before commit (AVIF, WebP, or high-quality JPEG)
- Strip EXIF metadata from public assets
- Set correct `width`, `height`, or `inferSize` for every image
- Mark LCP images with appropriate loading priority

## Local prep workflow: compress before commit

Before any image enters your Astro project, run this checklist:

### 1. Resize to display width × 2

Most marketing heroes display at 1200–1600 CSS pixels wide. Export at **2400–3200px max** to cover retina displays. Do not commit 6000px camera originals.

Open the <ToolLink tool="batch-image-compressor">batch image compressor</ToolLink>, set max dimension to 2400px, and export.

### 2. Choose the right format

| Asset type | Best source format for Astro |
| --- | --- |
| Hero photography | AVIF or WebP (Astro will optimize further) |
| Blog inline images | WebP or JPEG |
| UI screenshots | PNG or lossless WebP |
| Logos with transparency | PNG or SVG (use SVG when possible) |
| Product photos | WebP or AVIF |

For maximum compatibility, you can commit high-quality JPEGs and let Astro convert to WebP/AVIF at build time. For best performance, commit AVIF or WebP directly — Astro passes them through or optimizes minimally.

### 3. Strip metadata

Enable **Strip metadata** in Asset Melt's studio settings. Re-encoding removes EXIF GPS coordinates, device info, and timestamps before commit.

See [privacy-first image compression](/blog/image-compression/privacy-first-image-compression) for why metadata stripping matters for public repos.

### 4. Commit to src/assets or public/

**src/assets/** (recommended):
```
/src/assets/images/hero.avif
/src/assets/images/hero-mobile.avif
```

Import directly in components and Astro processes them:

```astro
---
import { Image } from 'astro:assets'
import heroImage from '@/assets/images/hero.avif'
---

<Image src={heroImage} alt="Hero" />
```

**public/** (unprocessed):
```
/public/images/hero.avif
```

Files in `public/` are served as-is without optimization. Use this for images you've already fully optimized or that don't need responsive variants.

Smaller committed files = faster clones, cheaper LFS, and faster builds before Sharp caching takes effect.

## Using the Astro Image component

### Basic usage with static import

```astro
---
import { Image } from 'astro:assets'
import heroSrc from '@/assets/images/hero.avif'
---

<Image
  src={heroSrc}
  alt="Asset Melt studio compressing images locally"
  loading="eager"
  inferSize
/>
```

**Key props:**

- `src` — imported object or URL string
- `alt` — required, descriptive alt text
- `loading` — "eager" for LCP image, "lazy" (default) for below-fold
- `inferSize` — automatically reads dimensions from imported images
- `widths` — array of responsive widths; defaults to [400, 800, 1200]

### Width and height (preventing CLS)

Always provide dimensions explicitly or use `inferSize`:

```astro
<Image
  src="/images/product.webp"
  alt="Oak dining table"
  width={1200}
  height={800}
  widths={[400, 800, 1200]}
/>
```

Or let Astro read them automatically for local imports:

```astro
<Image
  src={heroImage}
  alt="Hero"
  inferSize
/>
```

Without dimensions, browsers cannot reserve space, causing CLS when images load.

## Images in content collections

Astro's content collections provide type-safe image handling for blogs, docs, and markdown-heavy sites.

### Frontmatter images

```mdx
---
title: "My Blog Post"
heroImage: "./hero.avif"
---
```

### Schema validation

Define an image schema in your collection config:

```ts
// src/content/config.ts
import { defineCollection, z } from 'astro:content'
import { image } from 'astro:assets'

const blog = defineCollection({
  schema: z.object({
    title: z.string(),
    heroImage: image(),
    heroAlt: z.string(),
  }),
})

export const collections = { blog }
```

### Rendering in templates

```astro
---
import { getEntry } from 'astro:content'
import { Image } from 'astro:assets'

const post = await getEntry('blog', Astro.params.slug)
const { Content } = await post.render()
---

<Image
  src={post.data.heroImage}
  alt={post.data.heroAlt}
  inferSize
  loading="eager"
/>
```

This approach gives you type checking at build time and automatic optimization for all collection images.

## AVIF and WebP strategy in Astro

Astro's Image component converts formats at build time via Sharp. The output format is controlled by:

1. `format` prop on the Image component
2. `image.service.config.formats` in astro.config.mjs
3. Source format (if no conversion specified, Astro optimizes the original format)

### Should you pre-convert to AVIF before commit?

**Yes** when:

- The image is a hero or LCP candidate
- You want to minimize build processing time
- You need predictable source quality for all variants

**Let Astro convert** when:

- You're migrating existing JPEG assets gradually
- The CMS only accepts JPEG uploads
- You need one source format for simplicity

### Example: commit AVIF sources and let Astro handle fallbacks

```astro
---
import { Picture } from 'astro:assets'
import heroSrc from '@/assets/images/hero.avif'
---

<Picture
  src={heroSrc}
  formats={['avif', 'webp']}
  alt="Hero image"
  inferSize
/>
```

The Picture component generates `<source>` elements for each format, with browser fallbacks automatically.

Read [AVIF vs WebP](/blog/format-conversion/avif-vs-webp-2026) for format tradeoffs.

## Remote images and CDN sources

Astro can optimize remote images at build time. Configure allowed domains in astro.config.mjs:

```js
// astro.config.mjs
export default defineConfig({
  image: {
    domains: ['cdn.example.com'],
    remotePatterns: [
      {
        protocol: 'https',
        hostname: '**.unsplash.com',
      },
    ],
  },
})
```

Then use remote URLs directly:

```astro
<Image
  src="https://cdn.example.com/hero.jpg"
  alt="Hero"
  width={1920}
  height={1080}
/>
```

**Remote image notes:**

- Astro fetches, optimizes, and caches remote images at build time
- Subsequent builds reuse cached optimized variants
- Pre-compress remote sources at the CDN origin for faster builds
- Always provide explicit width and height for remote images

### CDN workflow

If you host images on Cloudinary, Imgix, or a custom CDN:

1. Pre-compress originals before uploading to the CDN origin
2. Use Astro's Image component with remote URLs
3. Let Astro optimize at build time for responsive variants
4. OR configure a custom image service for URL-based transforms

Even with CDN integration, **pre-compress originals before uploading**. CDN transforms work best when source files are already clean.

## Optimizing at build time

### Sharp configuration

Astro uses [Sharp](https://sharp.pixelplumbing.com/) for image processing. Tune settings in astro.config.mjs:

```js
export default defineConfig({
  image: {
    service: {
      entrypoint: 'astro/assets/services/sharp',
      config: {
        limitInputPixels: false, // Allow large source images
      },
    },
  },
})
```

### Responsive widths

Configure default responsive widths globally or per-image:

```astro
<Image
  src={hero}
  alt="Hero"
  widths={[400, 800, 1200, 1600]}
  sizes="(min-width: 1024px) 1200px, 100vw"
  inferSize
/>
```

The `sizes` attribute tells browsers which srcset width to fetch at each viewport size — critical for correct responsive delivery.

### SSG vs SSR modes

- **SSG (static)**: Images optimized at build time, output to `dist/`
- **SSR (server)**: Images optimized on first request, cached for subsequent requests

For SSG sites, all image processing happens once at build. For SSR, Astro caches optimized variants after first request — similar to Next.js behavior.

## Common Astro image issues

### CLS (Cumulative Layout Shift)

**Problem:** Image loads and pushes content down.

**Fix:** Always set `inferSize`, or provide explicit `width` and `height`:

```astro
<Image src={hero} alt="Hero" inferSize />
```

### Slow builds

**Problem:** Initial build takes minutes processing images.

**Cause:** Sharp processes every source image on first build.

**Fix:**
- Pre-compress aggressively before commit
- Use build caching (CI cache ~/.astro or dist/_astro)
- Reduce source dimensions to max needed display size

### Missing dimensions error

**Problem:** "Image is missing required width and height attributes"

**Fix:** Add explicit dimensions or use `inferSize` for imported images:

```astro
<Image src={imported} alt="Alt" inferSize />
<!-- or -->
<Image src="/image.jpg" alt="Alt" width={1200} height={800} />
```

### Format not supported

**Problem:** "Image format not supported: .heic"

**Cause:** HEIC is not a web-native format.

**Fix:** Convert HEIC to WebP or JPEG before commit. Use Asset Melt to batch convert iPhone photos.

### Remote image build failures

**Problem:** Build fails fetching remote images.

**Cause:** Network issues, incorrect URL, or missing domain config.

**Fix:**
- Verify remote URL is accessible
- Add domain to `image.domains` or `image.remotePatterns`
- Pre-download and commit images if remote source is unreliable

## Real-world workflow

**1. Export from design tool**

Export at 2400px max width, AVIF or WebP.

**2. Compress locally**

Drop files into Asset Melt, enable metadata stripping, export to `src/assets/images/`.

**3. Commit**

```bash
git add src/assets/images/hero.avif
git commit -m "feat: add hero image for Q4 campaign"
```

**4. Use in Astro component**

```astro
---
import { Image } from 'astro:assets'
import hero from '@/assets/images/hero.avif'
---

<section class="relative h-screen">
  <Image
    src={hero}
    alt="Q4 campaign hero: woman using laptop in cafe"
    loading="eager"
    inferSize
    class="object-cover"
  />
</section>
```

**5. Verify**

Run Lighthouse on mobile, check LCP element. If it's the hero image and LCP is under 2.5s on 4G, you're good.

## Astro vs Next.js vs WordPress compression

| Platform | Optimization approach | Your prep step |
| --- | --- | --- |
| **Astro** | Build-time Sharp processing; caches variants | Resize and format before commit |
| **Next.js** | Server-side on demand; caches variants | Resize and format before commit — see [compress for Next.js](/blog/image-compression/compress-images-for-nextjs-2026) |
| **WordPress** | Plugin-based; varies by CDN | Compress before media library upload — see [compress for WordPress](/blog/image-compression/compress-images-for-wordpress) |

Astro and Next.js share a similar philosophy: optimize at build/runtime, but rely on developers to provide clean sources. WordPress optimizes post-upload, so **local prep before upload** is even more critical.

## Content collections and image workflows

For blogs and documentation sites with many posts, Astro content collections shine. Here's a complete workflow:

### 1. Collection schema

```ts
// src/content/config.ts
import { defineCollection, z } from 'astro:content'
import { image } from 'astro:assets'

const blog = defineCollection({
  schema: z.object({
    title: z.string(),
    heroImage: image(),
    heroAlt: z.string(),
    publishedAt: z.date(),
  }),
})

export const collections = { blog }
```

### 2. Post frontmatter

```mdx
---
title: "How to Compress Images"
heroImage: "./hero.avif"
heroAlt: "Image compression workflow diagram"
publishedAt: 2026-09-07
---

Content here...
```

### 3. Template rendering

```astro
---
import { getCollection } from 'astro:content'
import { Image } from 'astro:assets'

const posts = await getCollection('blog')
---

{posts.map(post => (
  <article>
    <Image
      src={post.data.heroImage}
      alt={post.data.heroAlt}
      widths={[400, 800]}
      inferSize
    />
    <h2>{post.data.title}</h2>
  </article>
))}
```

This pattern scales to hundreds of posts with type safety and automatic optimization for every image.
