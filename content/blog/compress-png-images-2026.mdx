**PNG compression in 2026** splits into two workflows: **lossless optimization** for when pixel-perfect fidelity matters, and **lossy palette quantization** for when you need smaller files and can accept 256 indexed colors. Understanding which approach fits your image — and when to abandon PNG entirely for WebP or AVIF — determines whether you ship a 2 MB screenshot or a 120 KB export that looks identical.

This guide covers the full PNG optimization stack: why PNGs get huge, how lossless tools like OxiPNG work, when and how to apply palette quantization, hitting strict byte budgets, CLI recipes, and the decision points for staying with PNG vs switching formats.

## Why PNG files get huge

PNG is a lossless format designed for graphics, screenshots, and images with transparency. It preserves every pixel, which is both its strength and the reason file sizes balloon when misused.

### Common causes of bloat

| Problem | Impact | Fix |
| --- | --- | --- |
| **Oversized dimensions** | 4000px screenshot when 1200px renders | Resize before optimizing |
| **24/32-bit RGBA** | 4 bytes per pixel for full-color + alpha | Palette quantization to 8-bit indexed |
| **Unused alpha channel** | Extra byte per pixel even when opaque | Strip alpha or convert to RGB |
| **Metadata chunks** | EXIF, creation tools, ICC profiles | Strip with OxiPNG |
| **Poor filter selection** | Wrong row predictor reduces deflate efficiency | Let OxiPNG try all filters |
| **Low deflate compression** | Default zlib settings, not max | OxiPNG level 5–6 |

**Resize first, always.** A 3200×2400 screenshot resized to 1600×1200 drops to 25% of the pixels before any quality tradeoff.

## Lossless PNG optimization: OxiPNG and Zopfli

Lossless PNG optimization recompresses the image data without changing any pixels. The output decodes to an identical image but occupies fewer bytes.

### How lossless optimization works

PNG stores image rows as filtered byte streams, then compresses them with DEFLATE (the same algorithm as ZIP). A lossless optimizer:

1. **Tries multiple PNG filters** (None, Sub, Up, Average, Paeth) per scanline to find the most compressible arrangement.
2. **Recompresses with stronger DEFLATE settings** (higher search windows, more exhaustive dictionary matching).
3. **Reduces bit depth and color type** when possible (e.g., RGBA → RGB, 8-bit → 4-bit grayscale).
4. **Strips unnecessary chunks** (metadata, creation tool signatures, thumbnails).

### OxiPNG

[OxiPNG](https://github.com/shssoichiro/oxipng) is a Rust-based PNG optimizer that performs all the steps above. It is fast, widely used, and available as a CLI tool and WASM module.

**Typical savings:** 10–40% on average PNGs, sometimes 50%+ on poorly exported files.

**Command:**

```bash
oxipng --opt max --strip safe input.png
```

- `--opt max` runs the slowest but most thorough optimization (equivalent to level 6).
- `--strip safe` removes non-critical metadata.

**WASM in browsers:** Asset Melt uses `@jsquash/oxipng` for client-side optimization with the same filter/deflate logic.

### Zopfli PNG compression

[Zopfli](https://github.com/google/zopfli) is an open-source DEFLATE encoder from Google that produces smaller output than standard zlib by exhaustively searching for better matches. It is much slower but creates the smallest valid PNGs.

OxiPNG can optionally use Zopfli as its deflate backend:

```bash
oxipng --opt max --zopfli input.png
```

**Use when:** File size matters more than encoding speed (final web assets, not iterative design exports).

### Realistic expectations

Lossless optimization is safe but limited. If your PNG is huge because it is 6000×4000 with full RGBA, lossless tools might save 20%, but the file is still enormous. **Resize or quantize next.**

<Callout title="Lossless means identical pixels" variant="info">
After lossless optimization, you can decode the PNG and compare it pixel-by-pixel to the original — they match exactly. That is why lossless optimization is safe for source assets, archives, and any context where fidelity is contractual.
</Callout>

## Lossy palette quantization with pngquant

Palette quantization reduces a full-color 24-bit RGB or 32-bit RGBA image to an 8-bit indexed palette of up to 256 colors. The algorithm picks the best colors and applies dithering to smooth transitions. The result is lossy but often visually lossless for graphics, screenshots, and illustrations.

### Why 256 colors work

Many images do not use millions of colors — they use a few hundred distinct values with smooth gradients between them. A smart quantizer picks the 256 most important colors, maps every pixel to the nearest match, and dithers to hide banding.

**Typical savings:** 60–80% when converting 32-bit RGBA to 8-bit indexed.

### pngquant

[pngquant](https://pngquant.org/) is the standard tool for palette quantization. It uses a perceptual color space (based on human vision) to choose the palette and applies dithering to mask artifacts.

**Command:**

```bash
pngquant --quality=65-80 --speed 1 input.png --output output.png
```

- `--quality=65-80` sets minimum and maximum quality. pngquant aborts if it cannot reach the minimum.
- `--speed 1` is slowest but best quality (default is 4).

**With OxiPNG post-processing:**

```bash
pngquant --quality=70-85 input.png --output temp.png && oxipng --opt max temp.png
```

First quantize, then losslessly optimize the indexed result.

### libimagequant in Asset Melt

Asset Melt uses `@squoosh-kit/imagequant-wasm`, a WASM build of libimagequant (the library behind pngquant). You can enable **Reduce palette** in the PNG settings panel, tune the number of colors (2–256), and adjust dither level.

The workflow is: decode → quantize → encode with OxiPNG. The Studio applies both steps automatically when palette reduction is enabled.

### When quantization looks bad

- **Photographic gradients with few colors** — sky, skin tones. 256 colors may show banding.
- **Subtle shadows and highlights** — quantization crushes smooth transitions.
- **Already well-distributed color** — a photo that uses 10,000+ distinct colors will not compress well to 256.

**Solution:** Increase color count to 256, raise dither to 80–100%, or switch to lossy WebP/AVIF instead.

## Compressing screenshots and UI captures

Screenshots are PNG's natural home: sharp text, flat UI colors, transparency for overlays. But they also expose every mistake in export settings.

### Best practices for screenshots

| Context | Recommendation |
| --- | --- |
| **UI with small text** | PNG lossless or lossless WebP — no lossy compression |
| **Marketing screenshot (mostly UI)** | PNG with palette quantization (256 colors) |
| **Screenshot with photo content** | Lossy WebP quality 88–92, or AVIF |
| **Annotated diagram** | PNG lossless, or SVG if vector-based |

### Why lossy compression blurs text

JPEG and lossy WebP/AVIF apply block-based transforms that soften high-frequency edges. A capital "I" at 12px in a screenshot turns into a blurry smudge at WebP quality 70. PNG and lossless WebP keep every edge crisp.

**Export at exact display width or 2× for retina.** Do not export screenshots at 3000px when they display at 800px — resize before encoding.

### Handling transparency in screenshots

Many screenshots include semi-transparent overlays (tooltips, modals, shadows). PNG handles alpha gracefully. Lossy WebP with alpha can introduce fringing artifacts around edges.

**Test visually:** Export both PNG quantized (256 colors + dither) and lossy WebP quality 90. Compare at 100% zoom. If text stays sharp in both, pick the smaller file.

## Transparent product images and logos

Product cutouts and logos with transparency are PNG's second major use case. They need clean edges and often small file sizes for collection grids.

### Transparent product photos

E-commerce product images with transparent backgrounds (white background removed) can be enormous as 32-bit RGBA PNGs.

**Workflow:**

1. **Resize** to max display need (e.g., 1600px for product detail, 600px for grid thumbnails).
2. **Try lossless WebP first** — often 40–60% smaller than PNG with identical alpha.
3. **If PNG required**, apply palette quantization with 256 colors and dither 1.0 (100%).
4. **Post-process with OxiPNG** at level 5–6.

### Logos and brand marks

Logos with transparency should usually be **SVG**. If raster is required (e.g., email, legacy CMS), keep PNG lossless at exact display size.

Do not quantize logos unless file size is critical and you have verified edges stay sharp. A blurry logo looks worse than a slightly large file.

### When WebP beats PNG for transparency

Lossless WebP often compresses transparent PNGs 30–50% smaller while staying pixel-perfect. It is a safe substitute when browser support is acceptable (all modern browsers in 2026).

```html
<picture>
  <source srcset="/logo.webp" type="image/webp" />
  <img src="/logo.png" alt="Company logo" width="200" height="80" />
</picture>
```

Read [JPEG vs PNG vs WebP vs AVIF](/blog/image-compression/jpeg-vs-png-vs-webp-vs-avif) for format trade-offs.

## When to leave PNG for WebP, AVIF, or SVG

PNG is not always the answer. Knowing when to switch formats saves time and bytes.

### PNG works best for

- **Lossless graphics** where pixel fidelity is contractual (design source files, archival).
- **Screenshots with text** where lossy compression would blur.
- **Simple icons and logos** when SVG is not an option.
- **Intermediate editing files** where you will apply more transforms later.

### Switch to lossless WebP when

- **You need smaller transparent PNGs** for web delivery.
- **Browser support is acceptable** (2026: all modern browsers).
- **You want to save 30–50%** without changing pixels.

Asset Melt can encode lossless WebP via the WebP codec with `lossless: 1` option.

### Switch to lossy WebP or AVIF when

- **The image is photographic** (even with transparency).
- **Palette quantization creates banding** (gradients, soft shadows).
- **You need sub-100 KB files** and PNG cannot reach the target even quantized.

AVIF with alpha is excellent for transparent product photos where file size drives conversion performance. Use the <ToolLink tool="batch-image-compressor">batch image compressor</ToolLink> to test AVIF quality 55–65 with alpha.

### Switch to SVG when

- **The image is vector-based** (icons, logos, simple illustrations).
- **You want infinite scaling** without pixelation.
- **File size is a few KB** and you want no raster artifacts.

SVG is not suitable for photographs or complex raster screenshots.

### PNG vs AVIF for transparent photos

| Factor | PNG (quantized) | AVIF (lossy) |
| --- | --- | --- |
| **File size** | Moderate (with 256 colors) | Smallest |
| **Edge quality** | Sharp when quantized well | Can soften slightly |
| **Gradient handling** | May band at 256 colors | Smooth gradients |
| **Browser support** | Universal | Modern browsers (2026) |
| **Encode speed** | Fast | Slow |

**Practical approach:** Export both, compare visually, pick the smaller file if quality is equivalent.

## PNG in 2026: the Third Edition and modern context

The **W3C PNG Third Edition Recommendation** was published in 2025, updating the spec with modern extensions that had existed in practice but were not standardized.

### What changed in PNG Third Edition

- **HDR imaging via cICP chunk** — support for HDR10, HLG, PQ transfer functions.
- **APNG (Animated PNG) officially standardized** — multi-frame animation, previously a Mozilla extension.
- **eXIf chunk for EXIF metadata** — replaces the older tEXt-based workaround.

**Practical impact in 2026:** Browser support for APNG is universal, but few tools generate HDR PNGs. The spec is mostly a formal catch-up to existing practice.

### Should you use APNG for animation?

APNG works for simple animations (spinners, icon transitions), but for anything photographic or complex, use video (WebM/MP4) or convert to AVIF image sequences. APNG encodes each frame as PNG, which is inefficient compared to video codecs.

**Mention only:** Animated GIF replacement is better served by video or static WebP/AVIF. See the existing guide on [replacing animated GIFs](/blog/format-conversion/replace-animated-gif-webp-avif-video-2026) for details.

### PNG HDR in practice

As of late 2026, HDR PNG tooling is sparse. If you need HDR delivery, AVIF or JPEG XL (with caveats — see [JPEG XL guide](/blog/format-conversion/jpeg-xl-jxl-guide-2026)) are better bets. PNG HDR will matter more when CMS and browser stacks mature around it.

## Hitting a byte budget with PNG

Sometimes you have a hard cap: "this screenshot must be under 100 KB for the upload form" or "thumbnails cannot exceed 50 KB each." PNG's lossless nature makes size targets tricky.

### Target-size workflow

Asset Melt supports **size-budget encoding** for PNG. It works by:

1. Trying lossless OxiPNG first.
2. If still over budget, applying palette quantization with decreasing color counts (256 → 128 → 64) until the target is met.
3. Optionally allowing resize if the color search fails.

Enable **Size budget** in the Studio, set target bytes (e.g., 102,400 for 100 KB), and let the pipeline search automatically.

**CLI equivalent:**

```bash
# Try lossless first
oxipng --opt max input.png -o temp.png

# If over budget, quantize
pngquant --quality=60-80 --speed 1 temp.png --output output.png

# Check size, iterate color count if needed
```

### When 100 KB is impossible

Some complex transparent PNGs cannot fit 100 KB without severe quality loss. If you hit this wall:

1. **Reduce dimensions further** — a 1200px screenshot at 800px may fit.
2. **Switch to lossless WebP** — often 30–50% smaller.
3. **Switch to lossy WebP or AVIF** — test quality 85–90.

Do not keep hammering palette quantization down to 32 colors. It will look terrible. **Format change is better than an ugly PNG.**

Read [how to reduce image size under 100KB](/blog/image-compression/reduce-image-size-under-100kb) for a step-by-step decision tree across all formats.

## CLI recipes: pngquant and OxiPNG

### Recipe 1: Lossless optimization (safe for anything)

```bash
oxipng --opt max --strip safe input.png
```

**Use:** Final web assets, design handoff, archival.

### Recipe 2: Lossy palette quantization + lossless optimization

```bash
pngquant --quality=70-85 --speed 1 input.png --output temp.png
oxipng --opt max --strip safe temp.png -o output.png
rm temp.png
```

**Use:** Screenshots, UI captures, illustrations where 256 colors suffice.

### Recipe 3: Batch folder with pngquant + OxiPNG

```bash
for file in input/*.png; do
  pngquant --quality=70-85 "$file" --output "temp_$(basename "$file")"
done

oxipng --opt max --strip safe temp_*.png --dir output/
rm temp_*.png
```

**Use:** Marketing screenshot batch, product thumbnail refresh.

### Recipe 4: Maximum compression (slow, smallest output)

```bash
pngquant --quality=75-90 --speed 1 input.png --output temp.png
oxipng --opt max --zopfli --strip safe temp.png -o output.png
rm temp.png
```

**Use:** Final production assets where encode time does not matter.

### Recipe 5: Lossless only, no metadata

```bash
oxipng --opt 4 --strip all input.png
```

**Use:** Quick optimization when Zopfli is too slow, but you want metadata gone.

## Troubleshooting PNG compression problems

| Problem | Likely cause | Fix |
| --- | --- | --- |
| **File still huge after optimization** | Dimensions too large, or needs quantization | Resize first; try palette quantization |
| **Banding in gradients** | Too few colors (palette quantization) | Increase colors to 256, raise dither to 100% |
| **Blurry text after compression** | Applied lossy WebP/JPEG instead of PNG | Use PNG lossless or lossless WebP |
| **Colors look wrong** | sRGB vs Display P3 mismatch | Convert to sRGB before encoding |
| **Transparent edges have fringe** | Lossy WebP with alpha at low quality | Raise WebP quality to 88+, or use PNG/lossless WebP |
| **Optimization made file larger** | Input was already well-optimized | OxiPNG should never increase size; check command |
| **Cannot hit byte budget** | Image complexity exceeds PNG capability | Switch to lossy WebP or AVIF |

## PNG compression checklist

Before publishing PNG assets:

- [ ] Resize to display width × 1.5–2 for retina (not camera resolution)
- [ ] Run lossless optimization (OxiPNG level 5–6)
- [ ] If file is still large, try palette quantization (256 colors, dither 100%)
- [ ] Strip metadata for public web assets
- [ ] Compare visually at 100% zoom (faces, text, gradients)
- [ ] Test alternative: lossless WebP (often 30–50% smaller)
- [ ] If targeting strict byte cap, use size-budget encoding or manual iteration
- [ ] For logos, prefer SVG when possible

## When PNG is the right choice

PNG wins when:

- **Lossless fidelity is required** (design source, legal, archival).
- **Text must stay sharp** (UI screenshots, annotated diagrams).
- **Transparency with crisp edges** (logos, product cutouts with hard alpha).
- **You are editing intermediate files** where re-encoding would degrade quality.

PNG loses when:

- **File size matters more than lossless** (photographic content where lossy is fine).
- **Gradients and soft shadows need smooth compression** (AVIF handles better).
- **You need progressive loading** (PNG interlacing is chunky; JPEG progressive is smoother).

The format you choose should match the job. Do not default to PNG for photos. Do not default to JPEG for screenshots. Match format to content type.
